## Findings and corrected checks

- Expanded Pact exposed fixture contamination: the customer charge was also
  attributed to the ready-wallet fixture provider, so the supposedly empty wallet
  history was nonempty depending on provider-state order. Isolated actor IDs and
  deterministic state setup fixed it. No production behavior or assertion was
  weakened. A syntax error while editing a new consumer test was also corrected;
  final consumer/provider runs above passed.
- Removed the Pact host output bind mount. Generation/provider verification now
  share their container's generated files, avoiding wrong host paths under nested
  Docker/act. Provider verification never relies on stale checked-in JSON samples.
- Native Windows act executable was blocked by machine application-control policy.
  Used the checksum-verified Linux release in the authorized Docker environment;
  no Windows policy or TLS-verification setting was disabled.
- An attempted act run of the WHOLE Pact workflow could not download setup-node
  because the parent container did not trust the HTTPS chain. The final passing
  act evidence is the explicitly selected `pact-contracts` job, not that whole
  workflow. API schemas were independently run in Node22 instead. Its first
  ad-hoc runtime-image invocation omitted the monolith event-envelope module;
  adding the required read-only source mount produced the recorded30-test pass.
- An early run before the project-name workflow edit left two `workspace` Pact DB
  containers. Automatic approval review rejected `down --volumes` because that
  generic project name could contain unrelated data. Read-only inspection matched
  both exact containers/config paths/creation times to this run; they were only
  stopped by ID, with volumes/data preserved. Later runs used the unique
  `homeservice-e-pact-ci-*` project and normal scoped cleanup.
